# Phase 3: QA REVIEW

## IDENTITY

**Agent:** `agents/writer.md` (loaded automatically from METADATA `agent:` field)

**Phase-specific role:** Quality assurance reviewer. Systematically evaluate content against QA criteria, verify all claims against sources, check for undefined acronyms/jargon, and achieve 5.0/5.0 rating through revision cycles.

**Additional constraints:** 5.0/5.0 is a HARD GATE — no exceptions. Never self-approve without objective evaluation. Never skip claim verification. Never allow undefined acronyms or jargon (must define on first use — BLOCKING requirement).

---

## INPUT CONTRACT

**Receives:**
- Draft from Phase 2: `{output_dir}/draft.md`
- Research artifacts: `{output_dir}/sources.txt`, `{output_dir}/research-notes.md`
- QA criteria template: `templates/qa-criteria-custom.md` (or `qa-criteria-template.md`)

**Prerequisites:**
- Phase 2 (DRAFT) gate passed (draft complete, brand voice applied)
- draft.md exists in output directory

**Source:** `skills/write/phases/00-workflow.md` (workflow orchestrator)

---

## OBJECTIVE

**Goal:** Achieve a 5.0/5.0 QA rating through systematic review, claim verification, acronym checks, and revision cycles.

**Success criteria:**
- All 7 QA criteria rated 5/5
- Overall rating: 5.0/5.0
- All factual claims verified against sources
- All acronyms and jargon defined on first use
- Results documented in `{output_dir}/qa-review.json`

**Failure criteria:**
- Rating stuck below 5.0 after 3 revision cycles → present best version with documented remaining issues
- Critical source missing for major claim → return to Phase 1 if needed

---

## METHODOLOGY

**Systematic review against criteria.** Evaluate the draft against each of the 7 QA categories independently, then calculate the overall score. This prevents halo effects where strong performance in one area masks weaknesses in another.

**Claim verification is non-negotiable.** Every factual statement must trace to a source. Unsupported claims either get sources added or get removed.

**Acronym check is blocking.** Content must be accessible to readers without domain expertise. Every acronym and technical term must be defined on first use with a parenthetical explanation.

**Why 5.0/5.0:** This is a quality floor, not a stretch goal. Each criterion at 5 means "meets all standards" — not "perfect." Allowing 4s would accumulate minor issues that degrade overall quality.

## EXECUTION

### Step 1: Read QA Criteria

**Tool:** Read

Read the QA criteria template:
- `skills/write/templates/qa-criteria-custom.md` (if exists)
- Otherwise: `skills/write/templates/qa-criteria-template.md`

**Expected output:** QA criteria loaded
**On failure:** Use the 7 standard categories defined below

### Step 2: Comprehensive Review

**Tool:** Direct analysis

Evaluate draft against each criterion (1-5 scale):

**Category 1: Brand Voice & Tone**
- Consistent voice throughout
- Tone matches brand guidelines
- Perspective (first/second/third person) appropriate
- No tonal shifts or breaks

**Category 2: Content Quality**
- Accurate and well-researched
- Original insights (not just rehashing sources)
- Clear and well-structured
- Appropriate depth for audience

**Category 3: Technical Accuracy**
- Code examples valid and tested
- Technical details correct
- Best practices followed
- No outdated information

**Category 4: Source Integration**
- All claims supported by sources
- Citations accurate and accessible
- Sources properly attributed
- 10+ sources referenced

**Category 5: Formatting & Structure**
- Headers logical and hierarchical
- Lists and tables well-formatted
- Code blocks properly formatted
- No horizontal scroll (line length limits)
- Links valid and accessible

**Category 6: Accessibility & Clarity**
- Language accessible to target audience (90%+ comprehension)
- Concepts explained clearly
- Examples provided where helpful
- **All acronyms defined on first use** (BLOCKING)
- **Technical jargon explained in context** (no assumed knowledge)
- Industry terms clarified for general audience

**Category 7: Completeness**
- No placeholder content (TODO, TBD)
- All required sections present
- Conclusion provides value
- Call to action or next steps clear

**Rating scale per criterion:**
- **5** — Exceeds standards, exemplary quality
- **4** — Meets all standards, minor improvements possible
- **3** — Meets most standards, notable issues to address
- **2** — Below standards, significant revision needed
- **1** — Does not meet standards, major rewrite required

**Expected output:** Rating per category with specific feedback
**On failure:** If unable to evaluate a category, note the gap

### Step 3: Validate Claims Against Sources

**Tool:** Read + WebFetch (for verification)

For each factual claim in the draft:
1. Identify the claim
2. Find supporting source(s) from sources.txt
3. Verify the source actually supports the claim
4. Check citation is properly formatted

**Example:**
- Claim: "React hooks were introduced in version 16.8"
- Source: Official React documentation [1]
- Verification: PASS — Documentation confirms hooks in 16.8

**Fail conditions:**
- No source supports the claim
- Source does not actually support what the claim says
- Source is not credible or accessible
- Citation missing or incorrect

**Expected output:** Claim verification summary (total, verified, failed)
**On failure:** Flag unverified claims for revision

### Step 4: Check Acronyms and Jargon (BLOCKING)

**Tool:** Direct analysis

Scan the entire draft for:
- Technical acronyms (API, SDK, CLI, YAML, JSON, etc.)
- Financial terms (EBITDA, ROI, IRR, etc.)
- Industry-specific acronyms
- Domain-specific jargon

**For each term found:**
- Is it defined on first use with parenthetical explanation?
- Is the definition inline (not buried in footnotes)?
- Are subsequent uses (after first definition) acceptable without redefinition?

**Definition pattern:**
```markdown
CORRECT: "EBITDA (Earnings Before Interest, Taxes, Depreciation, and Amortization — a measure of cash flow)"
CORRECT: "API (Application Programming Interface)"
WRONG: "Just using EBITDA without definition"
```

**If ANY undefined terms found:**
1. STOP — this is a blocking issue
2. Add definition at first mention: "TERM (full expansion — brief explanation)"
3. Re-scan to ensure all terms defined
4. Proceed only after all terms defined

**Expected output:** All acronyms and jargon defined on first use
**On failure:** Add missing definitions to draft before proceeding

### Step 6: Revise if Needed

**Tool:** Read + Edit

If any criterion rated below 5:
1. Review specific feedback for that criterion
2. Revise content to address issues
3. Update `{output_dir}/draft.md`
4. Return to Step 2 for re-evaluation

**Common revisions:**
- Rewrite sections with voice inconsistency
- Add missing source citations
- Fix technical inaccuracies
- Improve clarity and accessibility
- Complete placeholder content
- Add acronym definitions
- Fix formatting issues

**Expected output:** Revised draft addresses all issues
**On failure:** Document remaining issues if unable to resolve

### Step 7: Achieve 5.0/5.0

**Tool:** Direct analysis

Final verification:
- All 7 criteria rated 5/5
- Overall rating: 5.0/5.0
- qa-review.json shows `"approved": true`

If not at 5.0 after revision: cycle back to Step 2 (max 3 cycles).

**Expected output:** 5.0/5.0 achieved
**On failure:** After 3 cycles, present best version with documented remaining issues
